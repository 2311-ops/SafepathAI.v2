<objective>
Replace the raster tile renderer behind SafePath's two map surfaces with `maplibre_gl`, so the
Live Map and the history route sheet both draw OpenFreeMap's **Liberty** vector-tile style
(`https://tiles.openfreemap.org/styles/liberty`) through the native MapLibre engine.

Purpose: OpenFreeMap serves vector tiles only - there is no raster endpoint - so a vector-capable
renderer is required to use it at all. The user chose it deliberately over staying on the current
raster source (RESEARCH.md, CONTEXT.md `<domain>`), accepting that this is a real library
migration rather than a URL swap.

Output: A single `VectorMap` widget that owns every interaction with the plugin; both screens
rebuilt on top of it with their existing Flutter marker widgets intact; the accuracy circle
re-expressed as a real-world-metre geodesic fill; a camera-command test seam that survives the
loss of a constructible map controller; both map widget tests running again without a native
platform view; and the project's Technology Stack table brought in line with what actually ships.
</objective>

<design_direction>
**One widget owns the plugin.** Every interaction with `maplibre_gl` lives in a new
`vector_map.dart`. The two screens describe *what* to draw (a list of marker specs, circle specs,
line specs) and never touch a plugin type. This keeps the migration surface auditable by grep,
lets both screens share the screen-space reprojection machinery instead of duplicating it, and
means a future renderer swap touches one file.

**Pins stay Flutter widgets, positioned in screen space.** The plugin's native symbol annotations
accept a registered bitmap plus style-spec text - they cannot host a widget tree. Rasterising
`LiveMemberMarker` into a PNG would destroy the `CachedNetworkImage` avatar, the Semantics label,
the design-token typography and shadows CLAUDE.md mandates, its seven passing unit tests, and
would force a re-raster on every location tick. Instead the pins render in a `Stack` above the
map, with their screen coordinates reprojected from the native projection via
`toScreenLocationBatch()`. This is MapLibre's own documented `custom_marker` pattern.

**Geometry goes native, presentation stays in Flutter.** The route polyline and the accuracy ring
carry no widget content and no tap target, so they become native annotations and get GPU rendering
and correct zoom behaviour for free. Anything with design-system styling, an image, a Semantics
label or a tap handler stays a Flutter widget.

**The accuracy circle must be metres, not pixels.** The plugin's circle annotation takes a radius
in *screen pixels*, which would make an "accuracy" indicator meaningless - it would stay the same
size on screen while the real-world area it claims to cover changed with every zoom step. So the
circle is generated as a geodesic ring polygon in Dart and drawn as a fill. `accuracyCircleRadius()`
in `staleness.dart` carries over completely unchanged.

**Flatness is enforced, not assumed (D-01).** Liberty declares no default pitch, so the map starts
flat - but the user could pitch it with a two-finger drag, and Liberty contains a building
extrusion layer that would then render in 3D. Tilt gestures are therefore disabled outright.
Rotation is disabled too, keeping the north-up orientation the current map has, which also makes
the compass control pointless and lets it be turned off to free screen space.

**Attribution moves to the native control.** OpenFreeMap's own TileJSON already carries the exact
legally-required string covering OpenFreeMap, OpenMapTiles and OpenStreetMap, and the renderer's
built-in attribution button surfaces it. A hand-written label would drift from it and
under-attribute OpenMapTiles. Position it bottom-right: the overlay card, the member rail and the
low-battery banner all occupy the top of the Live Map.

**Rail-card taps animate (~300ms) rather than jump.** D-03 gives Claude discretion here and
research recommends the animation as a UX improvement over the old instant jump; it is a strict
superset of the previous behaviour and is called out in the SUMMARY as an intentional deviation.

**Two test seams, because two different things break.** The old test-owned map controller cannot
survive - a real controller is only handed out by the native `onMapCreated` callback and is not
constructible in a widget test. It is replaced by a *camera-command sink*: the screen writes its
intent into it, production forwards that intent to the native camera, and the test reads the
intent back. Separately, any test that pumps a tree containing a native platform view throws on
the platform-views channel, so `VectorMap` accepts an injectable stand-in builder that tests swap
in for the native view while still exercising the overlay, the chrome and every empty/error state.
</design_direction>

**Step 1 - `mobile/lib/features/location/application/map_geometry.dart` (new). Test-first.**

Write `mobile/test/features/location/map_geometry_test.dart` first, covering every case in this
task's `<behavior>` block, watch it fail, then implement.

The file declares two things and imports nothing from the presentation layer or the plugin -
it is pure geometry, which is why it sits in `application/`:

- `MapPoint`: an immutable const-constructible value type carrying `lat` and `lng` as doubles,
  with value equality and `hashCode`. This is the app's own coordinate type; it exists so the
  screens never have to name a plugin type or a third-party coordinate type.
- `geodesicRing(MapPoint center, double radiusMeters, {int segments = 64})` returning
  `List<MapPoint>`: converts a metre radius into degree offsets using an earth radius of
  6378137.0 m, scaling the longitude offset by `1 / cos(latitude in radians)` so the ring stays
  circular on the ground rather than in degree space, then walks `segments + 1` steps around a
  full turn so the returned ring is closed. Return an empty list for a non-positive, NaN or
  infinite radius, and also when `cos(latitude)` is within 1e-9 of zero (a near-polar centre would
  otherwise divide by ~0 and emit garbage coordinates).

`VectorMap`'s state:

- Holds the native map controller (nullable until created), a `Map<String, Offset>` of marker id
  to screen position, and a `bool` style-loaded flag.
- `initState`/`didUpdateWidget`/`dispose` manage a listener on `widget.controller`. When it fires,
  forward the stored `CameraCommand` to the native camera as an **animated** move over roughly
  300 ms (D-03 discretion; see `<design_direction>`), targeting the command's lat/lng and zoom.
- On map created: store the controller and subscribe to it. It is a `ChangeNotifier` that fires on
  every camera movement - on each notification, if the camera is currently moving, reproject.
- On style loaded: set the flag, draw the annotations, then reproject. Never call a style or
  annotation API before this fires; it is a race even though 0.26.2 hardened the Android side
  against the resulting crash.
- On camera idle: reproject. This is what guarantees pins settle exactly on their coordinate after
  a fling, since the reprojection call is asynchronous over a method channel and visibly lags the
  basemap by roughly a frame during fast motion. That lag is expected and is what the official
  upstream example does; pins failing to *settle* would be the real bug.
- `didUpdateWidget` also redraws annotations when the circle or line lists have changed, and
  always reprojects when the marker list has changed.
- Reprojection: build one list of plugin coordinates from `widget.markers` and make a **single**
  batched screen-location call. Never loop a per-marker projection call - that is one method-channel
  round trip per pin per frame. Guard with a `mounted` check after the await before calling
  `setState`, and convert the returned element's x/y (they are numeric, not necessarily double)
  explicitly.
- Annotation drawing: clear previously-drawn fills and lines first, then for each `MapCircle` add a
  fill whose geometry is a single ring produced by `geodesicRing(...)` mapped to plugin
  coordinates, using `colorHex` for both fill colour and fill outline colour and `fillOpacity` for
  the fill; then add a companion line around that same ring with `outlineWidth` and
  `outlineOpacity`, because the fill option object exposes no outline **width** and the current
  2px accuracy border cannot otherwise be reproduced. For each `MapLine`, add a line with round
  joins. Confirm the annotation-clearing method names against the package source as instructed
  above; if the bulk-clear helpers are not present under the names you expect, track the handles
  returned by the add calls and remove them individually instead.

`VectorMap.build`:

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → third-party tile CDN | The renderer fetches style JSON, TileJSON, vector tiles, glyphs and sprites from `tiles.openfreemap.org` over HTTPS. The requested tile coordinates reveal the approximate map viewport to that host. |
| pub.dev / Maven / CocoaPods → build | A new plugin with native Android and iOS code enters the build graph, pulling transitive native SDK artifacts. |
| native platform view → Flutter UI isolate | The map is a native view composited into the same UI isolate that hosts the always-visible SOS button. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-3ZB-01 | Information disclosure | tile/style/glyph fetches to `tiles.openfreemap.org` | medium | accept | Identical trust posture to the public OSM tile host it replaces, and OpenFreeMap requires no registration, no API key and sets no cookies.
