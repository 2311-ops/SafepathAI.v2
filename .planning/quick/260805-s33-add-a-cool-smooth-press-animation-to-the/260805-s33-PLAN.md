<design_direction>
Motion guidance applied from the `ui-ux-pro-max` skill's motion and ux-guidelines data
(`data/motion.csv` row 1 "press feedback": 150-200ms, ease-out, transform/opacity only;
`data/ux-guidelines.csv` row 8 "Duration Timing": 150-300ms for micro-interactions; row 7
"Excessive Motion": animate 1-2 key elements per view; row 9 "Reduced Motion": always gate on
the OS setting; row 27 "Haptic Feedback": confirmations only, never per-frame) and from the
`ui-styling` skill's active-state convention (`active:scale-95` — a small, transform-only
press-in, translated here to a Flutter `Transform.scale`).

Three coordinated layers, one coherent gesture — no fourth decorative element:

1. **Disc press-in (transform only).** Scale 1.0 to 0.94 over 140ms `Curves.easeOutCubic` on
   pointer down; settle back to 1.0 over 220ms on release. As the hold charges, the disc sinks
   a further 0.04 (to ~0.90 at full charge) so the button reads as being pressed deeper the
   longer it is held.
2. **Ring becomes visible and progress-reactive.** Track alpha lerps 0.35 to 0.50, arc stroke
   thickens 4.0 to 5.5, and a small blurred glow head rides the arc's leading edge. The locked
   mint-to-red colour interpolation past 60% is unchanged — no new colours are introduced, and
   SOS red stays reserved for this control.
3. **Centre countdown.** "SOS" swaps to 3, then 2, then 1 while held, with a 180ms fade+scale
   cross-fade between digits, and swaps back to "SOS" on release or completion.

No new colour tokens. No new typography sizes — the digit reuses the existing
`AppTypography.code` role (24px/800 JetBrains Mono, monospaced so digits cannot jitter or
reflow as they tick), overriding only `color` to white and `letterSpacing` to 0.
</design_direction>

Edit `SosArmRingPainter` first.

Add two derived visual behaviours to the existing normal-motion path, both driven by the
existing `progress` field — do not add a second painter class and do not change `_ringRadius`:
- In `_paintTrack`, take `progress` as a parameter and set the track alpha to `0.35 + 0.15 * progress`
  so the track brightens as the hold charges.
- In `_paintArc`, set `strokeWidth` to `4.0 + 1.5 * progress` instead of the fixed 4, keeping
  `StrokeCap.round` and keeping the existing mint-to-red `Color.lerp` past 0.6 exactly as it is.
- Still in `_paintArc`, after drawing the arc and only when `progress > 0.02`, draw a leading-edge
  glow head: compute `headAngle = -pi / 2 + 2 * pi * progress`, place a filled circle at
  `center + Offset(cos(headAngle), sin(headAngle)) * _ringRadius` with radius `3.5 + 1.5 * progress`,
  using the same lerped arc colour and a `MaskFilter.blur(BlurStyle.normal, 3)` on the paint.
  This is the element that makes the charge read as alive rather than as a static meter.

The `reduceMotion` tick-mark branch stays exactly as written — no glow head, no thickening,
