<objective>
Swap the SOS emergency-contact fallback channel's Infrastructure implementation from the retired
Android-gateway SMS provider to the WhatsApp Business Cloud API (Meta Graph API), behind the
unchanged `ISmsGateway` seam, and wire Meta's genuine delivery-status callback into the existing
`SmsWebhookController` / `RecordSmsDeliveryStatusCommand` seam.

Purpose: the retired provider had no delivery-status webhook at all, so every SOS fallback send sat
at `Queued` (sent, unconfirmed) forever — an observability hole on the one channel where "did it
actually arrive" matters most. It also routed every message through one physical phone, a silent
single point of failure for an emergency alert. Meta's Cloud API gives HMAC-signed
sent/delivered/read/failed callbacks and carrier-independent routing.

Output: `WhatsAppOptions`, `WhatsAppSmsGateway`, `WhatsAppWebhookSignatureValidator`,
`WhatsAppDeliveryStatusParser`, a new `ISmsDeliveryStatusParser` Application seam, a raw-body
`RecordSmsDeliveryStatusCommand`, a GET subscription-handshake endpoint, complete removal of the
retired provider from `backend/src` and `backend/tests`, and refreshed
`docs/EXTERNAL-SETUP.md` / `.planning/STATE.md`.

**SOS-01 boundary (non-negotiable):** `SosAlertDispatcher` (including `DispatchSms` and
`ComposeSmsBody`) and `TriggerSosCommandHandler` change **only** in XML doc-comment prose. No
control flow, no ordering, no added awaits, no new dependency, no extra work on the SOS fast path.
The dispatcher already runs behind a fire-and-forget background scope and still must never write
`Delivered` itself. Any diff to those two files beyond comment text is a plan violation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend -> Meta Graph API (outbound) | A bearer access token with send + management scope crosses here on every SOS fallback send |
| Meta -> `POST /webhooks/sms/status` (inbound) | Fully unauthenticated public route; the only path in the system allowed to write `SosDeliveryStatus.Delivered` for the SMS channel |
| Meta -> `GET /webhooks/sms/status` (inbound) | Unauthenticated subscription handshake carrying an operator-chosen verify token |
| Infrastructure -> `SosDeliveryAttempt.FailureReason` | Exception text from the gateway is persisted and later surfaced to the sender's UI |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-WGL-01 | Information Disclosure | `WhatsAppOptions` / `backend/.env` | critical | mitigate | Access token, app secret, and verify token bind from configuration only; `.gitignore` already covers `.env`/`*.env`, re-confirmed in `<pre_flight>`; no credential default in `appsettings.json` or C#; Task 3 gates on a staged-file check for `backend/.env` |
| T-WGL-02 | Spoofing | `POST /webhooks/sms/status` | critical | mitigate | `WhatsAppWebhookSignatureValidator` recomputes HMAC-SHA256 over the exact raw body keyed with the Meta app secret, compares via `CryptographicOperations.FixedTimeEquals`, and refuses everything when the secret is unconfigured; validation runs inside the handler before any DbContext access, so no caller of the command can skip it |
| T-WGL-03 | Information Disclosure | `SosAlertDispatcher.DispatchSms` failure path | high | mitigate | The gateway translates every provider failure to a fixed, credential-free `InvalidOperationException` message; the raw provider error body and status code are logged server-side only, never returned to the caller or written to `FailureReason` |
| T-WGL-04 | Spoofing | `GET /webhooks/sms/status` handshake | medium | mitigate | `hub.challenge` is echoed only on an exact fixed-time verify-token match against configured `WhatsApp:WebhookVerifyToken`; blank configured token refuses; 403 on any other outcome |
| T-WGL-05 | Tampering | Template parameter injection via composed SOS body | medium | mitigate | The composed body is server-generated from a display name plus session coordinates (never recipient-controlled) and is whitespace-normalized before becoming a template parameter; the template itself is Meta-approved and immutable at runtime |
| T-WGL-06 | Denial of Service | Unauthenticated, un-rate-limited webhook route | low | accept | Carried forward from T-03-22: a single indexed lookup that no-ops on an unrecognized id is cheap, and rate-limiting risks dropping a genuine delivery receipt — degrading delivery truthfulness on the SOS channel for no real security gain |
| T-WGL-07 | Repudiation | Meta-side token revocation / template disapproval leaving sends silently failing | low | accept | Failures surface honestly as `SosDeliveryStatus.Failed` per-contact rows with a reason, and SignalR + FCM remain independent SOS channels — no single channel failure takes the emergency down |
| T-WGL-SC | Tampering | Package installs | high | mitigate | No new NuGet package is introduced: `HttpClient`, `System.Text.Json`, and `System.Security.Cryptography` are all in-framework. If any task finds itself reaching for a package, stop and raise it rather than installing |
