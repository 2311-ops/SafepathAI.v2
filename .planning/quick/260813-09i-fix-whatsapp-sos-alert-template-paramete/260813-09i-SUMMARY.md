# Quick Task 260813-09i: Fix WhatsApp SOS Alert Template Parameter Mismatch Summary

**Reshaped `ISmsGateway.SendAsync` from a single composed body string to an ordered
`IReadOnlyList<string> templateParameters` so the WhatsApp SOS send matches the operator's
actually-approved three-placeholder `sos_alert` template, fixing a Meta parameter-count mismatch
that was silently failing every real SOS SMS send.**

## Accomplishments
- `ISmsGateway.SendAsync`'s second parameter is now an ordered `IReadOnlyList<string>
  templateParameters`, deliberately superseding the 260812-wgl signature lock, with an XML doc
  comment explaining why (WhatsApp templates are inherently multi-placeholder; a single opaque
  string cannot represent what any real gateway needs to send).
- `SosAlertDispatcher.ComposeSmsTemplateParameters` builds exactly three ordered values — sender
  display name, a maps link built from the session's coordinates or the literal `Location
  unavailable` fallback when either is null, and an invariant-culture UTC timestamp — with the SOS
  fast path's `await` count (18) and `private readonly` field count (4) both provably unchanged,
  and `TriggerSosCommand.cs` byte-identical to the pre-task baseline (commit 3799947).
- `WhatsAppSmsGateway.SendAsync` projects `templateParameters` into one `WhatsAppTemplateParameter`
  per supplied value, in order, each independently passed through the (renamed, per-parameter)
  normalization helper, with a defensive guard substituting a single hyphen for any value that
  normalizes to empty — Meta rejects an empty placeholder and an SOS send must not fail on it.
- `LoggingSmsGateway` and the `NoOpSmsGateway` test double follow the new signature;
  `LoggingSmsGateway` logs the ordered parameter list joined by `" | "`.
- Tests pin the three-parameter arity and order (`Message_SendsThreeOrderedTemplateParameters`),
  the no-location fallback (`Message_FallsBackToLocationUnavailableWhenCoordinatesAreNull`), and
  per-parameter normalization across three dirty inputs parsed back out of the serialized request
  body via `JsonDocument`.
- `docs/EXTERNAL-SETUP.md` now instructs the operator to create the `sos_alert` template with three
  body placeholders (name, location link, timestamp) instead of one, with a concrete example body
  line, closing off the root cause for future template recreation.

## Decisions Made
- Deliberately superseded 260812-wgl's `ISmsGateway.SendAsync` signature lock: the operator's
  actually-approved template has three body placeholders, not one free-text parameter, so keeping
  the lock would have kept a channel that fails 100% of real sends.
- Kept the SOS fast path structurally provable: `SosAlertDispatcher`'s `await` count, dependency
  count, and `TriggerSosCommand.cs` are all mechanically verified unchanged (SOS-01 held).
- Per-parameter truncation (320 chars) carried forward from the old whole-body cap, applied to each
  of the three elements independently rather than the composed whole.
