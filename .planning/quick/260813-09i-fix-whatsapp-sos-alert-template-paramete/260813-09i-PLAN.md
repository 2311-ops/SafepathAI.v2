<objective>
Fix a correctness bug shipped in quick task 260812-wgl: the WhatsApp send path packs the entire
composed SOS message into a single template parameter, but the operator's actually-approved
`sos_alert` template has three separate body placeholders (`{{1}}` member name, `{{2}}` location
link, `{{3}}` timestamp). Every real send fails with a Meta parameter-count mismatch until the
seam carries an ordered parameter list instead of one string.

Purpose: The SOS emergency-contact fallback channel is currently unshippable. This is the last
code defect standing between the operator provisioning `backend/.env` and a working end-to-end
SOS send. It is a defect in already-shipped code, not new scope.

Output: `ISmsGateway.SendAsync` takes an ordered `IReadOnlyList<string>`; `SosAlertDispatcher`
builds exactly three ordered parameters; `WhatsAppSmsGateway` emits one template parameter per
supplied value; `LoggingSmsGateway` and the test doubles follow; tests pin the three-parameter
shape, the no-location fallback, and per-parameter normalization; the confirmed template shape is
recorded in `docs/EXTERNAL-SETUP.md` so it cannot be silently reintroduced.
</objective>

<superseded_constraint>
`260812-wgl-PLAN.md` `<interface_contracts>` declared:

> Locked, do not change: `ISmsGateway.SendAsync(string toE164, string body, CancellationToken
> cancellationToken = default)` returning `Task<SmsSendResult>`

and its `must_haves.truths` repeated the same lock. **That lock is deliberately and knowingly
broken by this plan.** It was written before the operator's approved template shape was known,
under the assumption that a WhatsApp template could accept one free-text body parameter. It cannot.
A single opaque string is structurally incapable of representing what a real WhatsApp gateway must
send, so keeping the lock would mean keeping a channel that fails 100% of real sends.

This supersession is scoped to the second parameter only. `SmsSendResult`, the method name, the
return type, `RecordSmsDeliveryStatusResult`, and the `webhooks/sms/status` route are all still
locked and must not change.
</superseded_constraint>

<interface_contracts>
The new, post-task contract — all four implementations and the one caller must agree:

```
Task<SmsSendResult> SendAsync(
    string toE164,
    IReadOnlyList<string> templateParameters,
    CancellationToken cancellationToken = default)
```

- `record SmsSendResult(string ProviderMessageId)` — unchanged.
- `templateParameters` is positional: index 0 feeds the template's first placeholder, index 1 the
  second, and so on. Its length is a property of the configured template, not of the seam; the
  gateway emits one parameter per supplied value and does not hard-code a count.
- Every element must be non-empty. Meta rejects an empty placeholder; there is no "omit it" option.

Existing implementations that must be updated (four, not three — `NoOpSmsGateway` is easy to miss):

| Implementation | File |
|---|---|
| `WhatsAppSmsGateway` | `backend/src/SafePath.Infrastructure/Sms/WhatsAppSmsGateway.cs` |
| `LoggingSmsGateway` | `backend/src/SafePath.Infrastructure/Sms/LoggingSmsGateway.cs` |
| `NoOpSmsGateway` (test double) | `backend/tests/SafePath.Application.Tests/Sos/AlertFanOutTests.cs` |
| `Mock<ISmsGateway>` setups (Moq) | `backend/tests/SafePath.Application.Tests/Sos/SmsFanOutTests.cs` |

The one production caller is `SosAlertDispatcher.DispatchSms`. `IPushSender.SendAsync` already
takes an `IReadOnlyList<string>` first argument, and `PushFanOutTests` already uses
`It.IsAny<IReadOnlyList<string>>()` — follow that existing house pattern rather than inventing a
new parameter-object type.
</interface_contracts>
