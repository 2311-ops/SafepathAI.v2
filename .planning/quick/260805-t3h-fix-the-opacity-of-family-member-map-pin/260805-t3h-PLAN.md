<root_cause>
Read this before touching anything. The root cause was confirmed by reading the source
during planning — it is NOT a guess, and it is NOT a regression of the earlier fix.

**Where the on-map pins actually come from.** Despite the task title naming `MemberMapPin`,
the pins drawn on the map are `LiveMemberMarker` (`live_map_screen.dart:252-345`), built into
the `MarkerLayer` at `live_map_screen.dart:134-169`. `MemberMapPin`
(`mobile/lib/shared_widgets/member_map_pin.dart`) is used in exactly ONE place —
the header identity pin inside `_LiveMapOverlay` at `live_map_screen.dart:408` — and it is
constructed there without a `recordedAt`, so its band short-circuits to `opacity: 1` and
the header pin is already fully solid. Both widgets nonetheless read their alpha from the
same helper, so the fix lands in one file and covers both.

**The actual defect.** `stalenessFor(Duration age)` in
`mobile/lib/features/location/application/staleness.dart:13-39` maps ping age to alpha:
1.0 under 2 minutes, 0.7 under 15 minutes, 0.45 under 1 hour, 0.3 beyond that.
`LiveMemberMarker.build()` wraps the ENTIRE marker `Column` — avatar circle, name label,
presence label, and battery readout — in a single `Opacity` using that value
(`live_map_screen.dart:286-287`). So a family member whose last ping is 20 minutes old has
their whole pin composited at 45% over map tiles, and past an hour at 30%, which is what
"too transparent" is describing. The 2-minute threshold is aggressive enough that a member
sits at 0.7 or lower most of the time.

**Why this is not a 260716-ue7 regression.** That task changed only the self path — it made
`opacity` short-circuit to `1.0` when `isSelf` (`live_map_screen.dart:274-278`) and
deliberately left family-member fading intact, locking that with the test
`family member marker still fades when its ping is stale`
(`live_member_marker_test.dart:144-179`, asserting `lessThan(1.0)`). That fix is still in
place and correct. This task is about the *other* branch — the non-self family pins whose
fade was preserved on purpose but is simply tuned far too dark.

**Therefore the fix is to raise the floor, not to delete the fade.** Deleting the fade would
break the 260716-ue7 guard and throw away a real signal. Keeping a shallow fade is safe here
because staleness is already communicated redundantly and explicitly: the
`Last seen N min ago` badge text, the amber badge treatment past 15 minutes
(`badgeIsAmber`), and `_MarkerPresenceLabel`'s online/offline text. Alpha is a secondary
cue and can afford to be subtle.

**Known, deliberately out of scope (do not change these).**
- `LiveMemberMarker` fades on ping age (`location.recordedAtUtc`) independently of
  `isOnline` presence, so a currently-online member with an old ping still dims. That
  coupling is presence/staleness semantics, and this task is forbidden from touching
  presence logic. Raising the floor fixes the visible symptom without going near it.
- The accuracy halo alphas (`0.15` fill / `0.40` border) on the `CircleLayer`
  (`live_map_screen.dart:129-130`) and inside `MemberMapPin` — an intentionally translucent
  GPS-accuracy halo drawn behind the solid pin, not the pin.
- `MemberMapPin`'s `_pulseOpacity` tween (1 → 0.3, `member_map_pin.dart:56-58`) — the
  intentional heartbeat pulse on the live-self dot.
- `_LiveMapOverlay`'s `TweenAnimationBuilder` opacity 0 → 1
  (`live_map_screen.dart:380-390`) — a one-shot entrance animation that settles at 1.
</root_cause>
