<objective>
Close the 03-04 Known Stub: `responder_alert_screen.dart`'s "Call sender" button currently opens a
blank OS dialler because no family member's phone number exists anywhere on the wire. Give `User`
an optional phone number, a `/me` endpoint to set it, a profile field to enter it, and expose it on
`SosSessionDto` scoped strictly to that session's actual delivery recipients.

Purpose: the Core Value promises a guardian can act on an SOS within seconds. A dialler that opens
empty forces the guardian to leave the alert, find the contact, and dial manually - the exact
friction the alert exists to remove.

Output: a nullable `PhoneNumberE164` column on `Users`; `PATCH /me/phone-number` mirroring the
existing display-name command/controller pattern and reusing `PhoneNumberNormalizer`; a
recipient-scoped `TriggeredByPhoneNumberE164` on `SosSessionDto`; a phone-number card in the mobile
profile screen; and a `_callSender()` that dials the real number when present and behaves exactly as
today when absent.
</objective>

<security_frame>
This adds a PII field to a wire payload, so the scoping rule is the feature, not a detail of it.

**What T-03-03 actually mitigated (03-01-PLAN.md):** `SosRecipientStatusDto` carries `DisplayName`
only, so `EmergencyContact.PhoneNumberE164` and `UserDeviceToken.Token` have no path into a
guardian-facing DTO. That threat was about **not leaking recipients' contact details to each other**.

**What this change adds:** the **triggering user's own** number, to the people that user's own SOS
was delivered to. That is a different subject and a different audience, and it does not reopen
T-03-03 - `SosRecipientStatusDto` is not touched at all, and no recipient's number is ever added.

**The invariant that must hold, stated as a check rather than a promise:** the field is non-null on a
payload only when the payload's audience is contained in that session's distinct `RecipientUserId`
set from `SosDeliveryAttempts`. Membership in the family is necessary but never sufficient.
</security_frame>

**`SosSessionProjection.ProjectAsync(db, session, ct)` has exactly six call sites**, and the caller's
identity is already in scope at every one of them:

| Call site | Audience | Correct caller id |
|-----------|----------|-------------------|
| `TriggerSosCommand.cs:55` (idempotent replay branch) | the sender | `command.CallerUserId` |
| `TriggerSosCommand.cs:164` (fresh trigger) | the sender | `command.CallerUserId` |
| `AcknowledgeSosCommand.cs:59` | the acknowledging guardian | `command.CallerUserId` |
| `CancelSosCommand.cs:54` (idempotent branch) | the sender (self-cancel only, D-05) | `command.CallerUserId` |
| `CancelSosCommand.cs:63` | the sender | `command.CallerUserId` |
| `GetSosSessionQuery.cs:38` | whoever called `GET /sos/{id}` | `query.CallerUserId` |
| `SosAlertDispatcher.cs:104` | **fan-out**, no single caller | see below |

`SosAlertDispatcher.DispatchSignalR` builds `recipientUserIds` at lines 84-88 from
`attempts.Where(a => a.RecipientUserId.HasValue).Select(...).Distinct()` and passes exactly that list
to `_broadcast.SosTriggered(...)`, which resolves to
`_hubContext.Clients.Users(recipientUserIds).SosTriggered(session)`. The broadcast audience is
therefore **already** exactly the recipient set and excludes the triggering user - so a dedicated
broadcast entry point is correct there, and nowhere else.

This matters because it is the **primary** path in practice: a connected guardian receives the
session over SignalR and `responder_alert_screen.dart`'s `_loadSessionIfMissing()` short-circuits
without ever calling `GET /sos/{id}`. Populating only the GET path would leave the number missing in
the common case.

**`SosSessionDto` is constructed in exactly one place** (`SosSessionProjection`), and no test in
`backend/tests/` constructs it directly - a new required positional member breaks nothing but the
projection itself.

**Existing patterns to mirror, verified:**
- `MeController` display-name PATCH: request record at file top, `_currentUser.UserId is not { } userId` guard returning `Unauthorized()`, handler call inside `try`, `catch (ArgumentException ex) => BadRequest(new { error = ex.Message })`, `Ok(ToResponse(result))`.
- `AddEmergencyContactCommandHandler` (03-05): `command.Region ?? _configuration?["Sms:DefaultRegion"]` then `PhoneNumberNormalizer.ToE164(input, defaultRegion)`; `IConfiguration` is an optional constructor parameter so unit tests construct the handler with just the db context.
- `EmergencyContactConfiguration`: phone column is `HasMaxLength(20)`.
- `20260713152701_AddUserProfileFields` is the template for a plain nullable-column-add migration on `Users`.
- Mobile `ProfileApi` is an abstract class with three implementers that must all be updated: `DioProfileApi`, `test/helpers/fake_profile_api.dart`'s `FakeProfileApi`, and `profile_controller_test.dart`'s private `_FakeProfileApi`.
- Mobile `SosSession` uses named optional constructor parameters, so a new optional field breaks none of the ~15 existing construction sites across the test suite.
</current_state>
