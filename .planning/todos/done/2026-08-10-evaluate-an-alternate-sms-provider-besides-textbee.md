## Problem

The SOS emergency-contact SMS fallback channel was just migrated from Twilio to TextBee
(quick task 260810-vcf, commits 2bc4367/b3f5ebe/047b1b1/8144421 on `phase/04-geofencing`),
switched to a free, self-hosted-Android-gateway model to avoid Twilio's cost and Egypt-specific
A2P filtering/pricing (Twilio charges ~$0.40/segment to Egypt without a registered Alpha Sender
ID, vs. ~$0.01 domestic-registered — see conversation 2026-08-10).

The user tested TextBee themselves and, independent of that result, flagged wanting to evaluate
a different SMS provider for the future. The known reliability gap driving this: TextBee routes
SMS through one physical Android phone running the TextBee app — if that phone loses power,
network, or the app stops running, SOS SMS sends silently fail to reach anyone. TextBee also has
no delivery-status webhook, so `TextBeeWebhookSignatureValidator.IsValid` is a permanent
unconditional `false` and every send is recorded as `Queued` (sent, unconfirmed) forever, never
`Delivered` — a real observability regression versus Twilio's webhook-confirmed `Delivered`
status, for the one channel (SOS) where "did it actually arrive" matters most.

Brevo was raised as a middle-ground candidate during the same conversation (carrier-routed,
pay-as-you-go like Twilio, no single-phone dependency) but its SMS-specific delivery-webhook
support was never confirmed (its docs page 403'd during research) before the user pivoted straight
to TextBee.

## Solution

**Decision locked (2026-08-11): WhatsApp Business Cloud API (Meta Graph API), full replacement of
TextBee — no dual-channel SMS fallback.** This directly answers the evaluation this todo originally
asked for: WhatsApp's Cloud API has genuine delivery-status webhooks (sent/delivered/read/failed via
`X-Hub-Signature-256` HMAC-signed callbacks), fixing TextBee's key gap (permanently-false
`ISmsWebhookSignatureValidator`, every send stuck at `Queued` forever). Brevo and Twilio-with-Egypt-
Alpha-Sender-ID were not pursued — WhatsApp was the user's explicit direction instead.

**Currently blocked:** the user has submitted a Utility-category WhatsApp message template (SOS
alert content, e.g. `sos_alert`) to Meta for approval and is waiting on that approval before
implementation can start. Do not begin the swap until the user confirms the template is approved —
sending a template message before approval will fail outright.

Note: the user also has a separate, unrelated `otp_verification` **Authentication**-category
template already approved — that one is NOT usable for SOS content (Meta locks Authentication
templates to OTP-only) and must not be touched or referenced by this work.

**Implementation plan for when unblocked** (mirrors the Twilio→TextBee migration pattern, quick task
`260810-vcf`, behind the existing unchanged `ISmsGateway` seam):
1. Build `WhatsAppSmsGateway` implementing `ISmsGateway.SendAsync` (signature locked), calling
   `POST https://graph.facebook.com/v22.0/{phone-number-id}/messages` with a **template** message
   type (required — SOS alerts are business-initiated and must work outside any 24h WhatsApp
   customer-service session window; freeform text messages are not usable for this). Confirm the
   exact current request/response JSON shape against `developers.facebook.com/docs/whatsapp/cloud-api`
   at implementation time rather than assuming it.
2. `WhatsAppOptions`: `WhatsApp:AccessToken`, `WhatsApp:PhoneNumberId`, `WhatsApp:WabaId`,
   `WhatsApp:TemplateName`, `WhatsApp:TemplateLanguage` — same `IsConfigured` zero-cost-default gate
   shape as `TextBeeOptions`; `LoggingSmsGateway` stays the free default for a fresh clone. Real
   secret values (access token, Phone Number ID `1190449597495068`, WABA ID `1605779661263531` —
   already generated by the user) go only into the local gitignored `backend/.env`, never into
   appsettings.json or any committed file.
3. Wire the delivery-status webhook (`X-Hub-Signature-256` HMAC-SHA256 over the raw body, signed
   with the Meta App Secret) into the existing `SmsWebhookController`/`RecordSmsDeliveryStatusCommand`
   seam — this finally gives the SOS channel a real `Delivered` status, unlike TextBee. Also needs
   the GET verify-token handshake (`hub.mode`/`hub.verify_token`/`hub.challenge`) Meta requires
   before it will send any callbacks at all.
4. Fully remove TextBee (delete `TextBeeSmsGateway.cs`/`TextBeeOptions.cs`/
   `TextBeeWebhookSignatureValidator.cs`, drop from DI, strip all references) with the same
   zero-references rigor used when Twilio was removed.
5. Update `docs/EXTERNAL-SETUP.md` (WhatsApp Business Platform setup: System User token, Phone
   Number ID / WABA ID lookup, Utility template creation/approval, webhook subscription) and
   `.planning/STATE.md`'s SMS-provisioning blocker.
6. `SosAlertDispatcher`/`TriggerSosCommandHandler` (SOS fast-path) must not change behaviorally —
   only the Infrastructure-layer gateway implementation swaps (SOS-01 non-negotiable).

**Next step:** once the user confirms Meta has approved the Utility template, resume via
`/gsd-quick` with this todo as the task description.

## Resolution (2026-08-12)

Executed via quick task `260812-wgl` exactly per the implementation plan above: `WhatsAppOptions`/
`WhatsAppSmsGateway` (Task 1), a signed `X-Hub-Signature-256` delivery-status callback + GET
subscription handshake wired into `SmsWebhookController`/`RecordSmsDeliveryStatusCommand` via a new
`ISmsDeliveryStatusParser` Application seam (Task 2), and a zero-reference sweep plus
`docs/EXTERNAL-SETUP.md`/`STATE.md` updates (Task 3). All `TextBee*` classes and references removed
from `backend/src` and `backend/tests`. `SosAlertDispatcher`/`TriggerSosCommandHandler` changed only
in doc-comment prose. See `.planning/quick/260812-wgl-migrate-sos-fallback-channel-from-textbe/260812-wgl-SUMMARY.md`
for the full record, including the WhatsApp Cloud API version/shapes assumed (WebFetch/WebSearch
tools were unavailable in that session) and the outstanding operator-side provisioning steps.
