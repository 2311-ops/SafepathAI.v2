## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Make the emergency reach a guardian who is not looking at the app. Today an SOS only lands on a guardian with the app open; after this plan it lands on their lock screen, and tapping it opens the responder screen for that exact session.

Purpose: SOS-02 names FCM as a required channel, NOTIF-03 requires the guardian to actually receive an SOS notification, D-19 requires the notification to deep-link straight into the responder screen, and D-32 requires a multi-device token model so a guardian with a phone and a tablet is alerted on both rather than only on whichever device they logged into last.

Output: the `IPushSender` seam with a Firebase-backed and a zero-cost logging implementation, per-device token registration, the FCM arm of `SosAlertDispatcher`, the mobile push service handling all three notification-tap lifecycles, and the platform configuration both mobile OSes require.

This is the third and final channel, completing D-06's "all three from day one" inside this phase.

Explicit non-goal: any duress or covert notification behaviour (D-28). The push payload names the sender and the session and nothing more.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → `POST /me/device-tokens` | A client asserts a push token that will subsequently receive emergency payloads containing another family member's identity and location. |
| backend → FCM | Outbound call authenticated by a service-account private key. |
| FCM → device | Emergency payload transits Google infrastructure. |
| device → `POST /sos/{id}/push-receipt` | A client asserts it received an emergency push, upgrading a delivery row to Delivered. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-23 | Spoofing | `RegisterDeviceTokenCommand` | high | mitigate | The owning user is taken from `ICurrentUserService`; registering a token already held by another user reassigns it to the authenticated caller rather than letting two users share it, so a stale registration cannot keep delivering a family's emergencies to a previous owner (asserted by `Register_ReassignsATokenThatMovedToAnotherUser`) |
| T-03-03 | Information Disclosure | `UserDeviceToken.Token` | high | mitigate | The token appears in no client-facing DTO and in no log line — `LoggingPushSender` logs only a count, enforced by this plan's negative grep |
| T-03-24 | Information Disclosure | FCM payload contents | medium | accept | The push carries the sender's display name, the session id and a timestamp so a lock-screen preview is actionable; it deliberately carries no coordinates and no phone number, so a shoulder-surfer learns only that a named family member needs help. Suppressing the name entirely would make the notification useless in the seconds that matter |
