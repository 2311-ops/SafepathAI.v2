## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Extend the emergency to people who do not have the app: a user's configured emergency contacts now receive an SMS with the alert and a location link, tracked with the same honest per-channel status as every other channel.

Purpose: D-11 defines SOS recipients as active Guardians plus configured emergency contacts, and plan 03-01 delivered only the Guardian half. `03-RESEARCH.md` Pitfall 2 established that no phone number exists anywhere in the schema today, so this is the slice that makes "SMS fallback" mean anything at all. D-06 requires the SMS channel from day one, and D-07/D-08 require the free path first.

SMS provider decision, closing the `STATE.md` blocker "Phase 3 (SOS): SMS-fallback provider choice needs a concrete decision during planning": the concrete choice is **Twilio behind an `ISmsGateway` abstraction, with `LoggingSmsGateway` as the registered default whenever credentials are absent** (D-07, D-08). Research compared Twilio, Vonage and Azure Communication Services and found Twilio has the most mature .NET SDK and the only well-documented delivery-status webhook among them, with a free trial credit that covers a graduation demo once recipient numbers are verified. The abstraction means the project has a working, testable, zero-cost SMS path with no account at all, and the paid path is a configuration change rather than a code change.

Output: the `ISmsGateway` seam and both implementations, emergency-contact CRUD, E.164 normalisation, the widened recipient resolution, the SMS arm of `SosAlertDispatcher`, and the signature-validated Twilio status webhook that makes the SMS channel's Delivered state truthful.

Explicit non-goal for this phase: sending SMS directly from the sender's own device. iOS cannot send SMS silently, so an Android-only implementation would create an asymmetric guarantee (D-16). Plan 03-07 instead surfaces a local "call this contact" action for the offline case.

This plan runs in parallel with 03-04 — it touches only backend files. The mobile emergency-contact management screen is plan 03-07, which pairs it with the offline fallback actions that use it.
</objective>

Create `SmsWebhookController.cs` with `[ApiController]` and route `POST /webhooks/sms/status`. It deliberately carries no `[Authorize]` attribute, because the caller is the SMS provider rather than an authenticated user — authenticity is established by signature instead.

Validate the request before doing any work: read the `X-Twilio-Signature` header and recompute the expected signature over the full request URL plus the sorted form parameters using the configured auth token, via the Twilio SDK's request-validator helper. Reject a mismatch with `Unauthorized()` and mutate nothing. Without this, anyone who learns the URL could forge delivery confirmations and make the sender's screen claim an SMS was delivered when it never was — a false confidence failure that D-10 exists to prevent. When no auth token is configured (the `LoggingSmsGateway` path), reject every request outright, since no legitimate provider callback can exist in that mode.

On a valid request, read the provider's message id and status form fields, find the `SosDeliveryAttempt` whose `ProviderMessageId` matches, and map the provider status: a delivered status sets `Status = SosDeliveryStatus.Delivered` with `DeliveredAtUtc = DateTime.UtcNow`; an undelivered or failed status sets `Status = SosDeliveryStatus.Failed` with the provider's error code recorded in `FailureReason`; a queued, sending or sent status is ignored, because the message has still only been accepted, not received. An unknown message id returns 200 without mutating anything so the provider does not enter a retry loop.

After a successful mutation, resolve the session's recipient user ids and call `IAlertBroadcastService.DeliveryStatusChanged` so the sender's open emergency session flips that SMS chip live.

Add `Twilio:StatusCallbackUrl` to `TwilioOptions` if it is not already there, and document in the SUMMARY that this must be a publicly reachable HTTPS URL — during local development a tunnel is required, and leaving it unset simply means the SMS channel stays at `Queued`, which is the honest state rather than a wrong one.

Do not attach any rate-limit policy to this route. Add the five webhook behaviours to `SmsFanOutTests.cs`.

| client → `/me/emergency-contacts` | A user submits a display name and a phone number that will later be dialled and messaged. |
| backend → Twilio API | Outbound call carrying an account SID, auth token and a recipient phone number. |
| Twilio → `POST /webhooks/sms/status` | An unauthenticated inbound request from the public internet that can change a delivery row's state. |
| application → log sink | SMS destination numbers pass through logging in the default gateway. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-03 | Information Disclosure | `EmergencyContactDto` | high | mitigate | `PhoneNumberE164` exists on exactly one DTO, returned only from the `/me/emergency-contacts` owner-scoped routes; `SosRecipientStatusDto` continues to carry `DisplayName` only, so no guardian-facing payload can carry a contact's number (enforced by this plan's DTO grep gate) |
| T-03-19 | Spoofing | `POST /webhooks/sms/status` | high | mitigate | `X-Twilio-Signature` is recomputed over the request URL and sorted form parameters with the configured auth token before any mutation; a mismatch returns `Unauthorized()` and, when no token is configured, every request is refused (asserted by `Webhook_RejectsAnInvalidSignature`) |
| T-03-20 | Elevation of Privilege | emergency-contact CRUD | high | mitigate | Owner id is always taken from `ICurrentUserService`; update and delete load the row first and reject when `OwnerUserId` differs from the caller (asserted by `Update_RejectsAContactOwnedBySomeoneElse`) |
| T-03-21 | Information Disclosure | `LoggingSmsGateway` log lines | medium | mitigate | The destination number is redacted to its last four digits before logging, so a shipped log sink never accumulates full emergency-contact numbers |
| T-03-08 | Tampering | Twilio credentials | high | mitigate | SID, token, from-number and callback URL are read from configuration only and never committed; the default registration with no configuration present is `LoggingSmsGateway`, so an unconfigured environment cannot accidentally spend or leak |
| T-03-15 | Repudiation | false SMS Delivered state | medium | mitigate | `SosAlertDispatcher`'s SMS arm can only write `Queued`; `Delivered` requires a signature-validated provider receipt, and an absent callback URL leaves the channel honestly at `Queued` |
| T-03-22 | Denial of Service | webhook flood | low | accept | The route does a single indexed lookup on `ProviderMessageId` and returns 200 for unknown ids without writing; adding a rate limit here risks dropping genuine receipts, which would degrade delivery truthfulness for no security gain |
</threat_model>
