## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Deliver the real-time half of the emergency: a dedicated `AlertHub` that pushes an SOS to every connected guardian within the same request, plus the acknowledge and cancel commands the responder and sender flows need.

Purpose: SOS-02 and NOTIF-03 require a real delivery channel with server-side acknowledgement tracking, and the Core Value requires that channel to be structurally isolated from routine location traffic. D-05 requires self-cancel to be a parallel follow-up that never delays or retracts the original alert; D-10 requires that dispatching to a channel is never reported as delivery.

Output: `AlertHub`, `IAlertClient`, `AlertBroadcastService`, the SOS-only `SosAlertDispatcher`, the acknowledge/cancel/get-session handlers, the hub route and its JWT query-token allowance in `Program.cs`, and the three backend Wave 0 test files this plan owns.

Channel scope here is SignalR only. Plan 03-05 adds the SMS channel and plan 03-06 adds FCM to the same `SosAlertDispatcher`, completing D-06's three channels inside this phase.

This plan runs in parallel with 03-02 — it touches only backend files, 03-02 touches only mobile files.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SignalR client → `/hubs/alert` | The JWT arrives in the query string (SignalR's WebSocket handshake cannot set headers), and the client asserts a `familyId`. |
| SignalR client → `AlertHub.ConfirmReceipt` | A client asserts that it received an emergency push, which flips a delivery row to Delivered. |
