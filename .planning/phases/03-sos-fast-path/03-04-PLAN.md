## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Close the loop for the second vertical slice: a guardian with the app open is now yanked to a full-screen responder screen when a family member triggers SOS, can acknowledge it and call the sender, and the sender's own session shows honest per-recipient, per-channel delivery state.

Purpose: SOS-02 requires visible delivery-acknowledgement tracking and NOTIF-03 requires the in-app SOS notification. D-18/D-20 forbid a dismissible card — the responder experience is full-screen and force-navigated. D-04 requires the sender's emergency session to show delivery confidence, guardian notification state and live-location sharing status; this plan delivers the first two, and plan 03-08 adds the live-location status to the same screen. D-09/D-10 forbid collapsing delivery into one checkmark or claiming Sent on a server acceptance. D-22 fixes the responder's action set to Acknowledge and Call sender.

Output: the `signalr_netcore` client for `/hubs/alert`, the responder controller and full-screen responder screen with the two Phase 3 actions, the four-state delivery status chip, the recipient list on the sender's session, and the responder widget test from `03-VALIDATION.md` Wave 0.

Explicit non-goals: a guardian "mark resolved" action (D-23), and any FCM-driven arrival path — plan 03-06 adds the push deep-link so an app that is closed or backgrounded also reaches this screen (D-19). Live-location rendering on the responder screen is plan 03-08 (D-21); the canceled state is plan 03-09 (D-24).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `/hubs/alert` → guardian device | Server-pushed emergency payloads carrying another family member's identity and coordinates arrive here and are parsed on-device. |
| guardian device → `POST /sos/{id}/acknowledge` | The guardian asserts they have seen an emergency, which upgrades a delivery row to its strongest state. |
| responder screen → dialler | A `tel:` intent hands a phone number to the OS. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-16 | Denial of Service | `SignalRSosHubClient` event handlers | high | mitigate | A try/catch inside every `connection.on` handler prevents a single malformed emergency payload from tearing down the connection carrying the rest of the emergency; asserted by "swallows a malformed payload without closing the stream" |
| T-03-17 | Tampering | stale reconnect race in the hub client | medium | mitigate | The `_generation` counter copied from `location_hub_client.dart` is re-checked after every await in `connect()`, so a superseded connection can never rewire the live streams |
| T-03-03 | Information Disclosure | responder screen rendering | high | mitigate | The screen renders only fields present on `SosSession`/`SosRecipientStatus`, which by construction carry `displayName` and never a phone number or device token; the Call-sender action hands the number to the OS dialler without displaying it |
| T-03-04 | Elevation of Privilege | `POST /sos/{id}/acknowledge` from this client | high | transfer | Enforced server-side in plan 03-03 by `RequireMembership`; the client cannot acknowledge on another recipient's behalf because the server derives the row from the authenticated caller |
| T-03-18 | Spoofing | forced navigation on an incoming push | medium | mitigate | Force-navigation fires only for events arriving on the authenticated, family-scoped hub connection; the controller additionally drops events whose `triggeredByUserId` is the current user, so a replayed self-event cannot loop the sender into a responder screen |
</threat_model>
