> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Locked Decisions Carried From CONTEXT.md (recap only — not re-litigated here)

These are already-decided contracts from `03-CONTEXT.md`; this document turns them into concrete visual/motion specs but does not reopen them:

- 64px circle, 3-second press-and-hold, circular progress ring, release-before-3s cancels with nothing sent (D-01, DESIGN-02).
- No second confirmation gate after the hold completes — SOS sends immediately (D-02).
- Post-send: full-screen emergency session, never a banner/bottom sheet (D-03).
- Self-cancel is a parallel, non-blocking, transparent follow-up — guardians see "triggered, then canceled" (D-05, D-24).
- Per-recipient/per-channel delivery status, never one generic checkmark; never claim "Sent" on a bare API-accepted/queued state (D-09, D-10).
- Offline: same full-screen session immediately, clear "not sent yet / retrying" state, local fallback actions (D-12, D-17).
- Responder experience is full-screen, force-navigated even from foreground, deep-linked from FCM (D-18, D-19, D-20).
- Responder actions in Phase 3: **Acknowledge** and **Call sender** only — no "mark resolved" (D-22, D-23).
- Backup trigger via `quick_actions` fires immediately, no re-arm hold (D-25, D-27). Android Quick Settings tile / iOS Widget are later.
- Zero duress/decoy UI or behavior in Phase 3 (D-28). The `kind` schema field is backend-only forward-compat and has no UI surface this phase (D-29).

### Press-and-hold arm ring — Flutter implementation spec (locked motion, concretized)

Source motion token (locked, do not redesign): *"SOS arm: circular progress fills over 3000ms (press-and-hold), stroke transitions mint→red past ~60%."*

Concrete build:

1. **Gesture wiring:** `GestureDetector` with `onTapDown`, `onTapUp`, `onTapCancel` (not `onLongPress*` — a raw down/up pair is required because progress must render continuously across the full 3000ms, not fire once at a threshold).
   - `onTapDown`: `HapticFeedback.selectionClick()` (light, confirms the touch registered) + `_ringController.forward(from: _ringController.value)`.
   - `onTapUp` / `onTapCancel` while `_ringController.value < 1.0`: `_ringController.animateBack(0, duration: const Duration(milliseconds: 200), curve: Curves.easeOut)` — a quick 200ms snap-back, distinct from the slow 3000ms fill, so a canceled arm reads instantly as "released" rather than lingering. No toast/confirmation copy is shown on cancel-before-arm (nothing was sent — mockup shows no such message).
   - Controller completion (`AnimationStatus.completed`, i.e. the full 3000ms held): `HapticFeedback.heavyImpact()` (distinct, single pulse — do not repeat/vibrate continuously during the hold, per "don't overuse vibration feedback") then immediately invoke the arm-complete callback (generate `sosSessionId`, push the Sender Emergency Session route). Do not wait for any animation to visually settle before firing — the callback must run in the same frame as completion (D-02: sends immediately, no added delay).
2. **Painter:** `AnimationController(vsync: this, duration: const Duration(milliseconds: 3000))` driving a `CustomPainter` (not `CircularProgressIndicator`, which can't do the color-transition-past-60% requirement cleanly). Draw:
   - A base track: 3px stroke, `Colors.white.withValues(alpha: 0.35)`, full circle, radius = 34–36px (just outside the 64px disc so the ring doesn't overlap the disc edge).
   - A progress arc: `startAngle = -pi/2`, `sweepAngle = 2 * pi * controller.value`, `strokeCap = StrokeCap.round`, stroke width 3–4px.
   - Progress arc color: `progress < 0.6 ? AppColors.accentMint : Color.lerp(AppColors.accentMint, AppColors.sosRedDeep, ((progress - 0.6) / 0.4).clamp(0.0, 1.0))!` — this reproduces "mint→red past ~60%" exactly as an interpolation, not a hard color swap, for a smoother read.
   - Wrap the painter in `RepaintBoundary` (isolates the 60fps ring repaint from the rest of the bottom-nav tree).
3. **Center label swap:** During the hold, the "SOS" label may optionally be replaced with elapsed-seconds text (`"1s"`, `"2s"`) for extra affordance — this is discretionary polish, not required; if added, use `AppTypography.caption` styling at white, and only update once per whole second (not every frame) to avoid visual noise.
4. **Dispose:** `_ringController.dispose()` in the button's `dispose()` — required (per Flutter animation-controller-lifecycle guidance); a leaked controller on the one button that lives for the app's entire foreground lifetime is a real leak, not a theoretical one.

### Accessibility for the hold gesture

- Wrap the button in `Semantics(button: true, label: 'Emergency S O S. Press and hold for three seconds to alert your guardians with your location.', onLongPress: _startArm)` **in addition to** the raw `GestureDetector`. TalkBack/VoiceOver's "double-tap and hold" gesture on a focused element maps to `onLongPress`, not to raw down/up tracking — without this explicit `Semantics.onLongPress` wired to the same start routine, a screen-reader user cannot arm the button at all. This is a hard requirement, not a nice-to-have, for a safety-critical control.
- Announce arm progress via `SemanticsService.announce('Holding, 1 of 3 seconds', TextDirection.ltr)` at 1-second intervals only (not every frame) — screen-reader spam during a 3-second hold would drown out the one announcement that matters (arm-complete).
- On arm completion, announce `'SOS alert sending'` before/as the route pushes, so a screen-reader user gets the same "it's happening" confirmation a sighted user gets from the haptic + screen transition.
- Do not rely on the ring's color alone to communicate progress or the mint→red transition threshold — the numeric/announced progress above is the non-visual equivalent (color-only-indicator is a flagged anti-pattern).

### Reduced-motion fallback

- Check `MediaQuery.of(context).disableAnimations` (Flutter's binding for the OS "reduce motion" / "remove animations" accessibility setting). When `true`:
  - The **3000ms timing itself is a safety mechanism (accidental-trigger prevention) and must not be shortened or skipped** — only the decorative stroke/color interpolation is removed.
  - Replace the smooth arc-with-color-lerp painter with a simple, non-animated step indicator: three short tick marks around the circle that fill solid `AppColors.sosRedDeep` one at a time (at ~1s, ~2s, ~3s), with no easing curve and no color gradient — a discrete, low-motion substitute that still conveys "how far into the hold am I."
  - The 200ms cancel snap-back becomes an instant reset (no animation) under reduced motion.
- This same `disableAnimations` check gates every other animated element in this spec (pulse rings, live-dot blink, `AnimatedSwitcher` transitions between session states) — see each relevant subsection below; do not implement it once and forget it elsewhere.

## Full-Screen Sender Emergency Session — State Machine

One route, one `Scaffold`, states swapped via a state-driven body (e.g. a sealed `SosSessionState` union rendered through `AnimatedSwitcher` with a 200ms `Curves.easeOut` fade — cross-fade only, never a slide/scale that could read as playful for an emergency screen). Chrome is **SOS-red-domain for the entire route** (this is the one part of the app where red-as-dominant-surface is correct, not a dilution of the reservation rule — the screen literally *is* the emergency).

| State | Entry condition | Background | Headline copy (locked from mockup where noted) | Body copy | Primary actions |
|---|---|---|---|---|---|
| **Offline / queued** | Arm completed, device has no connectivity | Red gradient `#DE3B40 → #8E1D22` (radial, matches mockup's "Red radial-gradient takeover") | "Not sent yet" | "Not sent yet, retrying… Last retry: {relative time}" (D-17) | "Call {emergency contact name}" (`Icons.call`), "Copy my location" (`Icons.copy_all`) — both local, work with no network |
| **Submitted to server** | Network available, request accepted, `sosSessionId` acknowledged by backend but no channel confirmed yet | Same red gradient | "Sending alert…" | "We've received your alert and are notifying your guardians." — never "Sent" here (D-10) | none (informational, transitions automatically) |
| **Delivering** | At least one channel dispatch attempted | Same red gradient, header shows pulsing SOS icon (mockup: "Red header w/ pulsing sos icon") | "Alert active · {elapsed} elapsed" (mockup-literal, mono elapsed timer) | Per-recipient/per-channel status list (see Delivery Status Vocabulary below) | "Call 911" (ink/dark button per mockup — the one non-red CTA on this screen, deliberately visually distinct as the highest-urgency action), "Hold to cancel alert" |
| **Live-active** | Live-location streaming window is open | Same red gradient | "Streaming your live location" with a live badge (blinking dot, see Motion below) | Explicit end time/countdown for the streaming window (D-21): "Live until {end time} · {mm:ss} remaining" | Same as Delivering |
| **Self-canceled** | User completes the hold-to-cancel gesture | Deep Teal `#0C3A3F` (not red — de-escalated; not green either, since "canceled" ≠ "confirmed safe") | "Alert canceled" | "You canceled this alert at {time}. Your guardians can see it was triggered and then canceled." | "Close" (returns to normal app) |

**Hold-to-cancel (D-05, D-24 concretized):** Cancellation is **not** a modal confirmation dialog (a dialog would add a decision-gate the parallel-cancel decision explicitly avoids) and **not** a single accidental-prone tap. It reuses the arm button's press-and-hold pattern at a shorter duration — **2 seconds** (Claude's discretion: short enough to feel responsive for a false-alarm correction, long enough to prevent an accidental brush from silently retracting a real emergency). Button label: **"Hold to cancel alert"** (locked copy, verbatim from the design source). Ring color: white-on-transparent (not mint→red — canceling isn't "arming," reusing the arm's color language here would be confusing); on 2s completion, `HapticFeedback.mediumImpact()` and immediate transition to Self-canceled state — the guardian-facing cancellation notice fires in parallel via the same channel infrastructure as the original alert, never blocking on it (D-05).

**Contrast note (verified, not assumed):** white text at full opacity on `#DE3B40` computes to ≈4.37:1 contrast — meets WCAG's 3:1 "large text/UI component" threshold comfortably but sits just under the 4.5:1 normal-text threshold. Rule: any text ≥20px/700+ (headlines, the elapsed/countdown timer) may sit directly on `#DE3B40`; any smaller secondary text (status rows, timestamps) must render over the gradient's darker end (`#8E1D22`) or on a `Colors.white.withValues(alpha: 0.12)` frosted card surface for the necessary contrast boost — do not place small white body text directly on the lighter `#DE3B40` zone.

## Delivery Status Vocabulary (per-channel, per-recipient — D-09/D-10)

A fixed 4-state vocabulary, each state pairs an icon + color + text (never color alone, per accessibility rule):

| Status | Icon | Color | Copy pattern | When it applies |
|---|---|---|---|---|
| Not yet attempted | `Icons.remove` (dash) | `AppColors.bodySecondary`-on-white-translucent (muted, not amber/red) | "—" | Channel hasn't been dispatched to yet (e.g. SMS fallback only triggers after SignalR/FCM timeout) |
| Queued / retrying | `Icons.schedule` | `AppColors.caution` (`#C98A2B`) — reused per the existing "non-SOS-red attention state" convention, appropriate here because a queued/retrying channel is an attention state, not the emergency itself | "Queued", "Retrying (attempt {n})" | Server accepted the session but this specific channel hasn't confirmed delivery |
| Delivered | `Icons.check_circle_outline` | `AppColors.safe` (`#2F9E6B`) | "Delivered", "Delivered · {time}" | Channel-level delivery confirmed (SignalR ack, FCM delivery receipt, SMS provider delivery webhook where supported) |
| Acknowledged | `Icons.check_circle` (filled) | `AppColors.safe` | "Seen · {time}" (matches mockup's "Delivered/seen" language) | Only reachable for in-app Guardians who tap **Acknowledge** on the Responder screen — this is a strictly stronger state than Delivered, never inferred from delivery alone |

**Never collapse this to one checkmark (D-09).** Each recipient row shows one status per channel attempted for them (e.g. Maya: SignalR=Acknowledged, FCM=Delivered; Dad: FCM=Delivered, SMS=Queued). Row layout: recipient name/avatar (reuse existing `MemberMapPin`-style avatar pattern from Phase 2 where available) + a horizontal list of channel chips, each chip = icon + `AppTypography.caption` (12px/600 mono, matches the existing "PENDING"/"ACTIVE" badge convention from Phase 1) in the status color.

## Live-Location Streaming Window & Pulse/Live Indicators (motion tokens — locked, not redesigned)

These are pre-existing locked motion tokens from `SYSTEM_DESIGN (1).md` — implemented here in Flutter terms, not reinvented:

- **SOS pulse ring** (expanding box-shadow, ~1.6–2.4s ease-out infinite): implement as a repeating `AnimationController` (duration **2000ms**, the midpoint of the locked 1.6–2.4s range — Claude's discretion within the locked band) driving a `CustomPainter` that draws an expanding, fading ring outward from the pulsing SOS icon: radius `Tween(begin: 0, end: 28).animate(CurvedAnimation(curve: Curves.easeOut))`, opacity `Tween(begin: 0.5, end: 0.0)` on the same curve, `controller.repeat()`.
- **Live-dot blink** (opacity 1→0.3, ~1s): `AnimationController(duration: const Duration(seconds: 1))..repeat(reverse: true)` driving a small filled circle's `Opacity`. Always paired with a static text label ("LIVE") next to it — the blink alone must never be the only signal that streaming is active (color/motion-alone is a flagged anti-pattern).
- **Reduced motion:** both of the above must check `disableAnimations` and, if true, render as static (pulse ring: single static outline, no animation; live-dot: solid, non-blinking, full opacity) — the "LIVE" text label already carries the meaning, so nothing is lost.
- **Live-location countdown display:** new typography role needed (see Typography section) — a large, monospaced, tabular-figure countdown (`mm:ss`) so digits don't jitter/reflow as they tick down; this is a correctness requirement (jittering countdown digits look broken), not decorative.

## Offline / Retry State — Motion & Copy

- No pulse/blink animation on the offline state — a calm, static red gradient background communicates "still an emergency" without implying active progress that isn't happening yet. Reserve motion for states where something is genuinely live.
- Retry cadence and copy: "Not sent yet, retrying… Last retry: {relative time}" (D-17, locked copy pattern) updates in place (`AnimatedSwitcher` on the timestamp text only, 150ms fade) each retry attempt — do not restart/re-render the whole screen per retry, which would read as broken/flickering.
- Local fallback actions ("Call {emergency contact}", "Copy my location") remain visible and tappable throughout the offline state — they must work with zero network (native `tel:` intent, `Clipboard.setData`).

## Backup Trigger (`quick_actions`) — UI Implications

- No dedicated screen. Invocation immediately performs the arm-complete action (generate `sosSessionId`, no hold, D-27) and lands directly in the Sender Emergency Session route at whichever of "Submitted to server" / "Delivering" / "Offline-queued" state matches actual connectivity at that instant — the state machine above is entered mid-way, not re-derived.
- No additional "triggered via quick action" badge/copy is required for Phase 3 (kept out of scope to avoid scope creep beyond D-25–D-27); if added later, it would be a small `AppTypography.caption` line under the headline, not a structural change to this state machine.

## Accessibility Contract (consolidated)

- Touch targets: SOS button 72px total footprint, all session-screen buttons ≥52px height — both comfortably above the 44×44px floor.
- Haptics: single light tap-confirm on arm-start, single heavy pulse on arm-complete, single medium pulse on cancel-complete — never continuous/looping vibration during a hold (overuse anti-pattern).
- Screen reader: `Semantics.onLongPress` wired identically to the raw gesture's start routine (hard requirement for the arm button to be usable via TalkBack/VoiceOver at all); throttled progress announcements (1/sec, not per-frame); arm-complete and state-transition announcements via `SemanticsService.announce`.
- Color is never the sole indicator: every delivery/session status pairs an icon + text copy + color (Delivery Status Vocabulary table, Self-canceled vs. Delivered color distinction).
- Reduced motion (`MediaQuery.disableAnimations`): gates the arm ring's color interpolation (falls back to discrete tick marks, timing unchanged), the pulse ring and live-dot blink (fall back to static), and session-state `AnimatedSwitcher` transitions (fall back to instant swap) — applied consistently everywhere motion appears in this spec, not only on the button.
- Contrast: white text on `#DE3B40` computes to ≈4.37:1 (verified) — safe for large/bold text (≥20px/700+), not safe for small secondary text without the darker gradient end or a frosted white card backing (see Session State Machine contrast note).
- Dynamic type / large system text: session-screen headlines and body text use the existing `AppTypography` roles, which already flow through Flutter's default text-scaling; the Countdown Large role should have a defined max-width/wrap behavior so a very large system font size doesn't clip `mm:ss` digits — test at largest accessibility text size before sign-off (per the pre-delivery checklist).
