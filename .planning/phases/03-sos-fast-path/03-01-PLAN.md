## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

> Derived by the planner from the ROADMAP Phase 3 `**Goal:**` line plus requirement SOS-01. The ROADMAP goal line is not yet written in three-slot user-story form — run `/gsd mvp-phase 03` if you want it rewritten canonically.

<objective>
Deliver the server half of the thinnest SOS slice: a family member's device can hand the backend a client-generated `sosSessionId` and get back a durable, idempotent emergency record with one delivery row per (recipient, channel) pair.

This is the first vertical slice's foundation — plan 03-02 attaches the press-and-hold button and full-screen sender session that call this endpoint, so a real user gains "I can hold the SOS button and the server confirms it received my alert" at the end of wave 2.

Purpose: SOS-01 requires a path that bypasses routine/AI processing entirely; D-15 requires that an offline retry storm can never manufacture duplicate emergencies; D-09/D-10 require per-channel delivery truth to be queryable rather than a single boolean. All three are schema-and-handler decisions that everything downstream depends on.

Output: The `Sos` bounded context's persistence layer (four entities, five enums, four EF configurations, one applied migration), the idempotent `TriggerSosCommand` handler, `SosController` with `POST /sos/trigger` and `GET /sos/{sosSessionId}`, and the backend test files listed in `03-VALIDATION.md` Wave 0.

Recipient resolution in this plan covers active Guardians of the caller's family (D-11, first half). Plan 03-05 extends the same `ResolveRecipients` method to also return `EmergencyContact` rows, completing D-11 inside this phase.

Explicit non-goals here, owned by later plans in this phase: real-time fan-out (03-03), SMS (03-05), FCM (03-06). Explicit non-goal for the whole phase: any duress/decoy behaviour (D-28) — the `Kind` field exists for forward compatibility only (D-29).
</objective>
