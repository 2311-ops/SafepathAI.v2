## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Make SOS work when the network does not. Pressing and holding with no signal now opens the same full-screen emergency session immediately, states plainly that nothing has been sent yet, retries in the background, survives the app being killed, and offers the two things that still work offline: calling a contact and copying your location.

Purpose: SOS-03 is the requirement, and D-12/D-13/D-14/D-15/D-17 are the shape it must take — same screen immediately, device-generated session id, persisted across restart, idempotent on the server, honest "not sent yet, retrying" copy with a last-retry timestamp and local fallback actions.

This plan also lands the emergency-contact management screen (D-30). The two belong together: the offline fallback action is "call {emergency contact name}", which is meaningless until the user has somewhere to enter one, and plan 03-05 built the backend for exactly that.

Output: the connectivity hint service, the offline queue and retry loop in `SosController`, the offline branch of the sender emergency session, the emergency-contacts screen and its API client, and the offline-path tests.

Explicit non-goal for this phase: sending an SMS directly from the sender's own device when offline. iOS cannot send SMS silently, so an Android-only implementation would give two users of the same product materially different safety guarantees (D-16). The local fallback is a user-initiated dialler call instead.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device storage → app | The pending trigger payload, including the user's last known coordinates, is persisted across process death. |
| client → `/me/emergency-contacts` | A user submits a phone number that will later be dialled and messaged. |
| app → OS clipboard | The copy-location action places precise coordinates on a system-wide clipboard. |
| app → OS dialler | The call action hands a stored phone number to the platform. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-10 | Information Disclosure | persisted pending trigger payload | low | accept | The payload is the user's own session id and their own last-known position on their own device; it is cleared as soon as the server confirms receipt. Encrypting it would trade a real availability risk (a failed decrypt losing a queued emergency) for a negligible confidentiality gain |
| T-03-25 | Information Disclosure | "Copy my location" clipboard write | medium | accept | The clipboard is user-initiated and system-wide by design; the action exists precisely so the user can paste their position into any messaging app when the network path has failed. It is never written automatically — only on an explicit tap |
| T-03-20 | Elevation of Privilege | emergency-contact mutations from this client | high | transfer | Enforced server-side in plan 03-05: the owner is derived from the JWT and update/delete reject a row owned by another user; the client cannot address someone else's contacts |
| T-03-26 | Denial of Service | unbounded retry loop | medium | mitigate | The backoff escalates and caps, and only network-class failures are retried — a validation or authorization rejection surfaces as an error rather than looping forever (asserted by "does not queue on a non-network failure") |
| T-03-02 | Tampering | duplicate emergencies from retries | medium | mitigate | The session id is generated in exactly one place and read from persistent storage on every retry and every cold start; server-side idempotency from plan 03-01 is the backstop (asserted by "reuses the same session id across every retry") |
</threat_model>
