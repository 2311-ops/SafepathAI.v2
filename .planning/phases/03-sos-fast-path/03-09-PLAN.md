## Phase Goal

**As a** family member in danger, **I want to** trigger an SOS that instantly reaches my guardians and emergency contacts with my live location, **so that** help can find me within seconds even if I have no signal, my phone is locked, or the app is closed.

<objective>
Close the phase with the two capabilities that make SOS safe to actually use: correcting a false alarm, and firing without unlocking into the app.

Purpose: SOS-05 requires a self-cancel that runs in parallel to and never delays the guardian alert, shaped by D-05 (parallel follow-up, never a silent retraction) and D-24 (the guardian keeps seeing it, now explicitly canceled). SOS-06 requires an OS-level backup trigger, shaped by D-25 (`quick_actions`, one API for Android App Shortcuts and iOS Home Screen Quick Actions) and D-27 (fires immediately, no arming hold — the user already made a deliberate choice by long-pressing the app icon and picking the action).

Output: the two-second hold-to-cancel control, the de-escalated canceled state on both the sender's and the guardian's screens, the `quick_actions` service wired to the same arm-complete entry point the button uses, and the final manual verification of the OS shortcut.

Explicit non-goals, deferred by decision rather than difficulty: an Android Quick Settings tile and an iOS Widget or App Intent entry point (D-26); power-button sequence and Back Tap detection, which have no third-party-app-facing API on either platform and carry real store-policy risk (03-RESEARCH.md Pitfall 3); and any Silent or Duress behaviour, which is Phase 6 (D-28).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS shortcut → app | An entry point outside the app's own UI can initiate an emergency, potentially before authentication has settled. |
| client → `POST /sos/{id}/cancel` | A client asserts authority to change the state of an existing emergency. |
| lock screen → app | The home-screen shortcut is reachable without unlocking on some launcher configurations. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-12 | Elevation of Privilege | `POST /sos/{id}/cancel` from this client | high | transfer | Enforced server-side in plan 03-03: only `session.TriggeredByUserId` may cancel, so no other family member — Guardian or not — can silence someone else's emergency |
| T-03-31 | Tampering | silent retraction of a real emergency | high | mitigate | Cancellation writes a status and an audit stamp and deletes nothing; the guardian's screen stays mounted with explicit canceled copy rather than dismissing, and the sender's delivery list stays visible (asserted by "keeps the delivery list visible after cancelling" and "does not auto-navigate away on cancellation") |
| T-03-11 | Spoofing | accidental cancellation | medium | mitigate | A two-second hold with no tap path and no dialog; a tap or a sub-two-second hold does nothing (asserted by "does not cancel on a single tap") |
| T-03-32 | Spoofing | shortcut invoked on an unauthenticated or wrong-user device | medium | mitigate | The shortcut is registered only while authenticated and cleared on sign-out; a pre-auth invocation is deferred and replayed once, and the server independently requires a valid JWT and family membership before creating any session |
| T-03-02 | Tampering | duplicate emergency from a repeated shortcut tap | medium | mitigate | The service refuses to re-arm while a session is already active and routes the user to the existing session; server-side idempotency on `sosSessionId` from plan 03-01 is the backstop |
